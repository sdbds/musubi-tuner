# Z-Image SOAR Minimal Spec

## Status

- Draft
- Scope: `zimage` first pass only
- Goal: add a minimal, low-risk, low-VRAM-increase SOAR-style training path to `zimage`
- Default policy: follow official HY-SOAR defaults where the parameter semantics still match; use a separate smoke-test profile for low-cost bring-up

## 1. Problem Statement

Current `zimage` training in Musubi Tuner is standard flow-matching supervision:

- sample `noise`
- build `noisy_model_input` and `timesteps`
- run one DiT forward
- optimize one MSE loss against the main target

This is simple, but it only supervises on the original trajectory. SOAR adds an auxiliary self-correction signal on off-trajectory points generated by the current model itself.

The question is not "should we add another loss term". The real question is:

- where to insert the rollout path in the current `zimage` loop
- how to build auxiliary points without rewriting the data pipeline
- how to avoid a large peak VRAM increase from the extra forward pass

## 2. References

- Paper: [SOAR: Self-Correction for Optimal Alignment and Refinement in Diffusion Models](https://arxiv.org/abs/2604.12617)
- Official repo: [Tencent-Hunyuan/HY-SOAR](https://github.com/Tencent-Hunyuan/HY-SOAR)
- Official training loop reference:

- Official auxiliary point construction:
  [`soar/utils/algorithm.py`](https://github.com/Tencent-Hunyuan/HY-SOAR/blob/main/soar/utils/algorithm.py)

## 3. Current Local Baseline

Relevant local paths:

- `src/musubi_tuner/zimage_train.py`
- `src/musubi_tuner/zimage_train_network.py`
- `src/musubi_tuner/hv_train_network.py`
- `src/musubi_tuner/zimage_cache_text_encoder_outputs.py`

Current `zimage` training loop in `src/musubi_tuner/zimage_train.py` does:

1. `get_noisy_model_input_and_timesteps(...)`
2. `compute_loss_weighting_for_sd3(...)`
3. `call_dit(...)`
4. `mse_loss(...)`
5. `backward -> step`

Current `zimage` target in `src/musubi_tuner/zimage_train_network.py` is:

- `target = latents - noise`

This is important because it is the opposite sign of the official SOAR velocity convention `z_1 - z_0` (`noise - clean`). This means the rollout helper must convert local predictions back to the standard SOAR sign, and the auxiliary target must be expressed in `zimage`'s local sign convention.

## 4. Constraints Discovered

### 4.1 Official SOAR uses CFG rollout

Official HY-SOAR generates rollout velocity with conditional and unconditional branches, then forms:

- `v_cfg = v_uncond + scale * (v_cond - v_uncond)`

### 4.2 Local `zimage` training data does not cache unconditional text states

`src/musubi_tuner/zimage_cache_text_encoder_outputs.py` only caches caption embeddings for the dataset caption itself.

First-pass implication:

- we cannot reproduce official CFG rollout without expanding the text-cache pipeline
- the minimal version must use conditional-only rollout

Therefore v1 is not "paper-faithful SOAR". It is a `SOAR-lite` design that keeps the self-correction structure but uses:

- `v_rollout = v_cond.detach()`

instead of CFG rollout.

### 4.3 VRAM increase must be controlled by graph lifetime, not by optimizer tricks

The main extra memory risk is not the rollout itself. The main risk is retaining both:

- main loss graph
- auxiliary loss graph

at the same time.

So the first-pass design must avoid "compute both graphs first, backward once at the end".

### 4.4 `--fused_backward_pass` should be treated as incompatible in v1

The current `zimage` path supports `--fused_backward_pass` for Adafactor. The minimal SOAR implementation needs explicit control of:

- main backward
- aux rollout under `no_grad`
- aux backward
- single optimizer step

So v1 should reject:

- `--soar` together with `--fused_backward_pass`

instead of trying to support both immediately.

## 5. Scope

### In Scope

- add an experimental `SOAR-lite` path to `zimage`
- keep default training behavior unchanged when SOAR is off
- use ODE-only, single-path rollout
- support configurable auxiliary point count per rollout path
- use existing cached caption embeddings only
- minimize peak VRAM increase by serializing backward passes

### Out of Scope

- exact reproduction of official CFG-based SOAR
- SDE rollout variants
- multiple rollout paths
- generic cross-architecture abstraction for `zimage + flux2 + qwen_image + hv`
- `flux2` implementation
- unconditional text-cache redesign

## 6. User-Facing API

First pass should avoid a generic `--training_method` abstraction. That is premature for one architecture and one new method.

First pass should expose the knobs that actually affect v1 behavior, instead of hardcoding them. It should not expose fake compatibility flags that have no effect in `zimage` v1.

Proposed v1 CLI:

- `--soar`
  - enable `SOAR-lite` for `zimage`
- `--soar_lambda_aux`
  - float, default `1.0`
  - scales the auxiliary correction loss
  - default follows the official HY-SOAR setup
- `--soar_trajectory_length`
  - int, default `6`
  - number of auxiliary points sampled from the same rollout path
  - default follows the official HY-SOAR setup
- `--soar_num_sampling_steps`
  - int, default `40`
  - number of sampler steps used to define rollout step size
  - default follows the official HY-SOAR setup

Parameters intentionally **not** exposed in `zimage` v1:

- `cfg_scale_sampling`
  - not meaningful in cond-only rollout because there is no unconditional branch
- `num_rollout_paths`
  - not meaningful in ODE-only deterministic rollout; multiple paths would be duplicated work, not new information
- `sde_rollout_type`
  - unsupported in v1
- `sde_noise_scale`
  - unsupported in v1

Rationale:

- lower implementation cost
- lower test surface
- easier to compare against current baseline
- avoids pretending we already support paper-faithful CFG or stochastic rollout
- keeps the CLI honest: every exposed flag must change behavior

Smoke-test profile for first bring-up:

- keep the recommended defaults for `--soar_lambda_aux` and `--soar_num_sampling_steps`
- override only `--soar_trajectory_length 1`

This separates two concerns cleanly:

- user-facing defaults reflect the closest official SOAR configuration that still makes sense locally
- smoke tests minimize extra compute without changing the intended default behavior

## 7. Proposed Training Design

### 7.1 Main principle

Keep the existing main flow-matching loss exactly as-is, and append one auxiliary self-correction branch only when `--soar` is enabled.

### 7.2 Main step

Main step remains unchanged:

1. build `noisy_model_input` and `timesteps`
2. run normal `zimage` forward
3. compute weighted main MSE loss
4. `accelerator.backward(loss_main)`

### 7.3 Auxiliary rollout step

Under `torch.no_grad()`:

1. take the detached main prediction `v_rollout`
2. compute one ODE rollout step from `t0` to `t1`
3. obtain a new latent state `z_t1`
4. sample `args.soar_trajectory_length` auxiliary sigmas in a bounded interval above `sigma_t1`
5. interpolate from `z_t1` toward the noise endpoint `z_1`
6. build auxiliary points `z_t_prime_i`

The helper logic should be adapted from the official `single_step_aux_points(...)`, but only keep:

- ODE path
- one rollout path
- configurable auxiliary point count

### 7.4 Auxiliary target

Official SOAR notation uses:

- `z_0` = clean latent
- `z_1` = sampled noise
- `v_gt_standard = z_1 - z_0`
- `v_corr_standard = (z_t_prime - z_0) / sigma_t_prime`

Local `zimage` uses the opposite target:

- `target = latents - noise = z_0 - z_1`

Therefore the `zimage` auxiliary branch must do two explicit conversions:

- rollout uses `v_standard = -model_pred.detach()` before calling the official-style auxiliary-point builder
- auxiliary supervision uses `v_corr_zimage = (z_0 - z_t_prime) / sigma_t_prime`

### 7.5 Auxiliary forward

Run extra grad-enabled DiT forwards on each `z_t_prime_i` using the existing caption embedding from the same batch.

Then compute:

- `loss_aux_i = weighted_mse(v_pred_aux_i, v_corr_i)`

and normalize over the configured auxiliary points:

- `loss_aux = mean(loss_aux_i for i in trajectory_length)`

Backward should preserve this normalization even when points are processed serially, for example by applying:

- `args.soar_lambda_aux / args.soar_trajectory_length`

to each auxiliary backward call.

### 7.6 Optimizer step order

The required order is:

1. forward main
2. backward main
3. `no_grad` rollout
4. forward auxiliary
5. backward auxiliary
6. single `optimizer.step()`
7. single `optimizer.zero_grad()`

This order keeps peak VRAM much closer to the current baseline than a "sum all losses and backward once" implementation.

## 8. Required Refactor

### 8.1 `src/musubi_tuner/zimage_train_network.py`

Current `call_dit(...)` mixes two responsibilities:

- running the transformer forward
- building the main training target

That is awkward for SOAR because the auxiliary branch needs:

- the same forward path
- a different target

Minimal refactor:

- extract a helper that only predicts velocity, for example `predict_velocity(...)`
- keep `call_dit(...)` as the current wrapper for the main path

Pseudo-shape:

```python
model_pred = self.predict_velocity(args, accelerator, transformer, batch, noisy_model_input, timesteps, network_dtype)
target = latents - noise
return model_pred, target
```

The auxiliary branch should call `predict_velocity(...)` directly.

### 8.2 `src/musubi_tuner/zimage_train.py`

Changes needed:

- add parser args `--soar` and `--soar_lambda_aux`
- validate incompatible flags
- branch training loop into:
  - current path when SOAR is off
  - main + aux serialized path when SOAR is on
- log `loss_main`, `loss_aux`, and final displayed loss

### 8.3 Small helper module

Add one small helper module, recommended name:

- `src/musubi_tuner/soar_utils.py`

It should contain only the math that is genuinely reusable:

- `t_to_sigma_timestep(...)`
- `sigma_to_t(...)`
- `build_single_step_ode_aux_points(...)`

Do not add SDE branches or architecture-specific wrappers in v1.

## 9. Functional Requirements

### FR-1: SOAR must be opt-in

When `--soar` is absent:

- behavior must remain equivalent to current `zimage` training

### FR-2: Auxiliary supervision must be on-policy

When `--soar` is enabled:

- auxiliary points must be generated from the current model prediction of the same batch

### FR-3: No new dataset cache format in v1

First-pass `zimage` SOAR must work with the current text-cache format.

That means:

- no unconditional text-cache file
- no dataset recache requirement

### FR-4: VRAM growth must be bounded

The implementation must not intentionally retain main and aux graphs simultaneously.

### FR-5: Failure mode must be explicit

If the user enables unsupported combinations, training must fail early with a clear message.

Initial unsupported combination:

- `--soar` + `--fused_backward_pass`

## 10. User Stories and Acceptance Criteria

### US-1

As a trainer user, I can enable SOAR for `zimage` with one explicit flag, so I can compare baseline and self-correction training without rewriting my config.

Acceptance criteria:

- Given an existing `zimage` training config
- When I add `--soar`
- Then training starts without requiring dataset recache
- And `args.soar_trajectory_length` auxiliary correction points are executed per batch

### US-2

As a trainer user, I can keep baseline behavior unchanged when SOAR is disabled, so current scripts do not regress.

Acceptance criteria:

- Given a current config without `--soar`
- When I run training
- Then the training path matches current behavior
- And no SOAR-only validation or rollout path is triggered

### US-3

As a trainer user with limited VRAM, I can enable the first SOAR version without a disproportionate peak memory jump, so the feature stays usable on existing setups.

Acceptance criteria:

- Given `--soar` is enabled
- When one training step runs
- Then rollout happens under `no_grad`
- And auxiliary backward runs after main backward
- And the implementation does not keep both graphs alive until the final backward
- And changing `--soar_trajectory_length` changes compute cost without changing the semantics of `--soar_lambda_aux`

### US-4

As a trainer user, I receive a clear error if I pick an unsupported optimizer mode, so debugging cost stays low.

Acceptance criteria:

- Given `--soar --fused_backward_pass`
- When training starts
- Then startup fails early
- And the error message explains that v1 SOAR requires explicit backward control

## 11. Logging

Recommended new logs:

- `loss/main`
- `loss/aux`
- `loss/total`
- `soar/enabled`
- `soar/trajectory_length`

The progress bar can still show one compact scalar, but tracker logs should keep the split visible.

## 12. Implementation Order

1. Refactor `zimage_train_network.py` to expose forward-only prediction helper
2. Add `soar_utils.py` with ODE-only helper math
3. Add parser flags and early validation in `zimage_train.py`
4. Insert serialized SOAR path in the training loop
5. Add logging
6. Verify:
   - baseline path unchanged with SOAR off
   - SOAR path runs one step with `--soar_trajectory_length 1`
   - SOAR path runs with default `--soar_trajectory_length 6`
   - unsupported flag combinations fail early

## 13. Risks

### Risk-1: cond-only rollout may underperform official SOAR

This is expected. The first pass optimizes for:

- lower implementation cost
- compatibility with current `zimage` cache format
- faster iteration

### Risk-2: auxiliary branch may destabilize early training

Mitigation:

- keep the public default aligned with official HY-SOAR where semantics still match
- use `--soar_trajectory_length 1` for initial smoke tests

### Risk-3: trying to generalize too early will slow delivery

Mitigation:

- do not introduce a repo-wide `training_method` abstraction in v1
- do not mix `zimage` and `flux2` into the same first patch

## 14. Follow-Up After v1

If `zimage` SOAR-lite is stable, the next steps should be:

1. add optional unconditional text-state path for CFG rollout
2. measure whether CFG materially improves over cond-only rollout
3. only then port the helper shape to `flux2`

That order is cheaper than building a generic multi-architecture SOAR framework up front.
